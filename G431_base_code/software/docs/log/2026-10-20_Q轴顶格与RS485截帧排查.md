# Q 轴顶格与 RS485 截帧排查

## 实测事实

用户状态：Id 指令 0.15 A，Iq 指令 0 A；截图 Q 轴曲线存在正向顶格平台。源码上位机绘图会把超出显示范围的值裁到上下边界，因此图顶不等于真实电流上限。

关闭上位机串口后，本轮只读取 COM11、921600、8N1，约 5 秒收到 29673 字节，未发送控制命令。原始记录：`results/uart_q_jump_capture.bin`。

工程 V2 解析器结果：2 个有效帧、1246 次 CRC 拒绝、0 次协议格式错误、29586 重同步字节。两帧分别为：

| 帧号 | ADC 序号 | Id* A | Id A | Iq* A | Iq A |
|---|---:|---:|---:|---:|---:|
| 11114 | 13051023 | 0.15 | 0.152 | 0 | -0.021 |
| 11115 | 13081863 | 0.15 | 0.125 | 0 | 0.017 |

正常四通道帧长 32 字节。搜索帧头所得间隔主要为 21 字节（317 次）、22（230 次）、27（170 次）、28（167 次），32 字节仅 2 次。大量片段包含相同帧号和 ADC 序号，说明同一队首样本在被重复发送；这与发送失败后保留队首的代码逻辑一致。

Q 轴数值位于四通道帧的末尾，截断尤其影响该字段及 CRC。当前有效数据不足以认定 Q 轴失控，也不足以证明全部顶格值都是传输造成。现有 Python 解析器使用有符号 int32 且拒绝 CRC 错帧，没有发现简单的“负数按无符号显示”错误。CRC8 并非无碰撞校验，不能把它当作绝对可靠性保证。

## 根因判断及修复

旧串口适配层使用 HAL_UART_Transmit，超时 2 ms，无论是否发完都拉低 PA8 释放 RS485。20 kHz 控制中断可能延迟阻塞发送；超时后队首保持，主循环再重试，符合实测的短帧与反复重发模式。

直接证据为串口截帧；“中断负载触发超时”为代码与现象支持的判断，尚未用目标板超时计数器进一步确认。

修改：

1. USART1 TX 改用 DMA1_Channel3、DMA_REQUEST_USART1_TX；编码器保留 Channel1/2。
2. 发送前复制完整帧到静态缓冲，DMA 不引用主循环栈上临时数组。
3. 主循环轮询 DMA 完成及 UART TC；只有最后停止位发完才拉低 PA8。
4. 返回值区分 accepted=1、busy=2、error=0；busy 不推进队首，也不增加传输错误。
5. 主循环每轮调用 Service，队列空时也能收尾。
6. DMA 错误或超过 100 ms 进入故障状态；撤销 DMA 请求，待 UART 完成再释放方向，不无限重试半帧。
7. 增加 g_waveform_uart_completed / g_waveform_uart_dma_errors，分别计物理发送完成与 DMA 异常。原 sent_frames 表示已接受发送，不再代表线上完成。

未修改 PI 增益、采样配置和相电流保护来掩盖波形问题。
