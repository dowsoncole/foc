# 2026-10-22：PA0编码器通讯标记与逻辑分析仪核对

## 1. 本次要求与结论

用户最新要求：PA0专门指示编码器通讯，从SPI事务发起到接收数据解析结束一直为高，其余时间为低。用户测到约5 μs，明显小于NSS低电平约24 μs。

本次确认旧固件定义为PA0=FOC、PD2=编码器，和最新要求相反。约5 μs对应旧FOC回调，不是完整编码器通讯时长。已修正定义、编译、下载，并完成整个Flash加载区读回逐字节核对。新波形中，编码器标记覆盖NSS低电平并延续到解析之后，正常事务约29 μs。

这解决的是探针定义与测量含义错误，不等于编码器CRC故障已经解决。本次500 rpm启动复测仍出现CRC错误，输出已关闭；不能宣称已达到可靠最高转速。

## 2. 引脚与逻辑分析仪对应关系

| 分析仪通道 | 板端信号 | 当前含义 |
|---|---|---|
| CH0 | PA7 / MOSI | 主机命令 |
| CH1 | PA6 / MISO | 编码器返回 |
| CH2 | PA5 / SCK | SPI时钟 |
| CH3 | PA4 / NSS | 低电平期间选择编码器 |
| CH4 | PA0 | 编码器完整异步事务与解析，高电平有效 |
| CH5 | PD2 | FOC回调执行区间，高电平有效 |

CH4/CH5对应板端引脚的判断结合本次接线、源代码和交换前后的实际波形；不是根据通道颜色猜测。若现场换线，应以板端引脚为准。

旧记录中的PA0=FOC、PD2=编码器是历史固件定义，不修改历史文件以掩盖这次变更。后续以本文件及`Core/Inc/timing_probes.h`为准。

## 3. 修改内容与完整生命周期

新增`software/servo_v1/Core/Inc/timing_probes.h`，集中定义两个探针，使用GPIO BSRR原子置位/复位，避免多个模块分别硬编码同一引脚：

- `TimingProbe_EncoderBegin()`：PA0置高。
- `TimingProbe_EncoderEnd()`：PA0置低。
- `TimingProbe_FocBegin()`：PD2置高。
- `TimingProbe_FocEnd()`：PD2置低。

编码器周期采样路径位于`Modules/Encoder/Src/encoder.c`：

1. TIM1周期中断检查初始化及事务忙状态。未初始化或已有事务进行中时，不生成新的脉冲。
2. 记录事务起点，设置`transfer_busy`，紧接着PA0置高。
3. 调用`MT6835_SPI_TransmitReceiveAsync()`，启动六字节SPI/DMA。
4. 发起函数返回并不拉低PA0。DMA在CPU执行其它代码期间继续传输，PA0仍保持高。
5. SPI完成路径等待传输完成、释放NSS，调用`Encoder_TransferComplete()`。
6. 完成回调执行解码、CRC校验、状态检查、角度合理性检查，以及有效快照发布或错误记录。坏帧恢复也发生在标记有效区间内。
7. 回调末尾才拉低PA0，随后释放`transfer_busy`。这两步处于短临界区，防止下一次TIM1事务刚置高又被旧回调拉低。
8. 启动失败时显式拉低PA0并记录错误；传输错误和超时Abort通过完成回调统一收尾，不假装存在一次成功解码。

`Modules/Current_Sampling/Src/current_sampling.c`在控制回调前后操作PD2。`Core/Src/gpio.c`初始化两引脚低电平并更新注释；`Core/Src/stm32g4xx_it.c`同步修正FOC探针注释。

PA0测的是本工程正常周期编码器采样事务的完整软件生命周期，不是仅SCK脉冲串，也不是异步API调用所占CPU时间。传输失败时它表示从尝试开始到失败处理结束的区间，可能比正常事务短或长。

## 4. 为什么约24 μs与约29 μs都可能正确

当前SPI配置为168 MHz时钟源、64分频，即2.625 MHz；模式3、六字节，共48位。

纯48位时钟时间为`48 / 2625000 = 18.286 μs`。NSS低电平还包含片选建立、DMA启动及完成处理前的片选保持，所以实测约23～24 μs。PA0再包含发起前的软件开销和NSS释放后的解码/快照发布，所以约29 μs。

因此不能把“完整通信24 μs”直接理解为48位纯时钟时长，也不能要求PA0恰好与NSS完全等宽。按用户要求，正常PA0应覆盖NSS低电平，并在解析结束之后才下降。

中断抢占会计入PA0与PD2的墙钟时间。DMA通信和CPU运算可以并行，两个标记重叠本身不是数据竞争的充分证据；必须结合快照发布时间、数据年龄、DMA忙、错误计数及实际截止时间判断。此次没有通过强行串行等待掩盖错误，也没有降低CRC与数据新鲜度保护。

## 7. 交换后的复测与仍未解决的问题

交换后设置10秒深度（1 GSa，100 MHz），保留CH0～CH5，并另行发起500 rpm启动复测，未增加电流或速度上限。逻辑分析仪显示CH4为宽编码器脉冲、CH5为较窄FOC脉冲，正常PA0局部自动测量约29.25 μs，覆盖NSS低电平并延伸至解析结束。**后续完整离线核对发现，这段逻辑采集未捕获可与启动RAM错帧对齐的事件，不能当作启动故障的同步波形。**

新PA0不存在“只持续5 μs、发送尚未完成已下降”的现象。PA0的约29 μs与约23 μs NSS低宽之差包含解析收尾，符合用户定义。PD2此时是故障后输出关闭的短回调，不能将3.43 μs与旧基线4.93 μs比较后声称交换GPIO使FOC性能提高。

### 7.2 独立保存的启动RAM结果

启动仍失败，具体证据：

- `g_speed_run.enable=0`，state=4，fault=4，输出已关闭。
- `g_speed_test.feedback_fault=2`，表示CRC错误；数据年龄`0x7B8D`周期，约188.3 μs。
- CRC计数从0增加到397；alarm=0、角度跳变错误=0、busy_trigger=0，未因这次测试放宽保护。
- 首个RAM坏帧：`FF FF B5 1F FF FF`，接收CRC为FF，计算应为4D。
- 最后一个保存坏帧：`FF FF B5 FF FF FF`，计算CRC为0E。
- 故障后TIM1 BDTR=`0x02002054`，MOE位为0；CPU仍在运行。

对应原始记录：`results/spi_logic_20261022_probe_map_start.log`、`..._start_capture.bin`（312字节）、`..._start_capture.json`。这里的elapsed_s只在进入速度运行状态后计时，不能拿它直接反推预充起点。

交付前再次通过不暂停CPU的SWD读取：`enable=0`，TIM1 BDTR仍为`0x02002054`，CPU状态Running。记录位于`results/spi_logic_20261022_probe_map_final_off.log`。此次未重新启动电机来人为改变故障现场。

这提示故障不一定需要电机已经高速旋转，也可能在启动预充/中性PWM阶段发生。源码中预充顺序为：MOE关闭设置CCR=0等待1 ms→开启全低侧保持10 ms→切三相50%中性等待1 ms→main额外中性保持20 ms→armed并启动控制器。只有相关时间接近，尚不构成供电扰动或开关干扰的根因证明。

下一步需重新取得**明确覆盖故障时间**的采集，再匹配逻辑分析仪线上的首个坏帧与RAM字节，区分“线上本来已错”与“线上正确而MCU接收错误”。当前十秒数据没有建立这条时间对应关系。本次没有把硬件供电、电气干扰或FOC抢占任意一项直接宣称为已证实根因。

## 8. 最短复核方式

用户无需运行终端。本次代码已下载；保持当前接线，重新采集，观察PA0/CH4是否先于NSS下降置高、后于NSS上升且解析结束才置低；PD2/CH5单独观察FOC。阈值使用1.65 V，采样100 MHz。不要拿交换前的旧缓存波形检查新固件。

需要离线复算时，实际可执行脚本为`software/control_analysis/scripts/analyze_spi_logic.py`，不是只写在日志中的伪代码。该脚本按模式3解析完整48时钟帧，计算CRC并保留不完整帧排除原因；配套`test_analyze_spi_logic.py`有13项回归测试。输出文件采用新文件名，拒绝覆盖已有证据。
