# 编码器 SPI 逻辑分析仪异常诊断

> 诊断日期：2026-10-22
> 依据数据：`control_analysis/results/2026-10-22_16-04-35.txt`（8813 帧）
> `control_analysis/results/spi_logic_20261022_probe_map_start.csv`（200007 帧，转动工况）
> 解析工具：`control_analysis/scripts/analyze_spi_logic.py`
> 相关代码：`Modules/Encoder/` 全部（mt6835.c / spi1_encoder.c / encoder.c）
>
> **文档更新（同日）**：第 8 节已按修复后的代码现状重写——SPI 提速（10.5 MHz）、
> GPIO VERY_HIGH、坏帧恢复链重构、CRC 初值确认（0x00）均已落地；剩余方向为硬件级抗扰，
> 见 8.4。第 1 节 TL;DR 中的"进入需 RCC 复位才恢复的坏状态"描述对应修复前的旧固件行为，
> 恢复链已重构（8.2）。

## 1. 结论（TL;DR）

**线上（传感器 → MCU 引脚）的 CRC 一个都没错。** 两份逻辑分析仪数据合计 20.8 万帧，
**CRC 错误帧 = 0**；但转动工况下出现 **27 帧"时钟数不为 48"** 的异常帧，全部成对出现、
间隔恰好 1 帧。这指向：**MCU 的 SPI 外设接收到了边沿错位的帧，进入项目已记录的
"需 RCC 复位才恢复的坏状态"，导致固件反复捕获 CRC 错——问题在 MCU 接收侧，不在编码器、
不在线缆、也不在 CRC 公式。**

## 2. 数据来源与通道映射

| 通道 | 信号 | 说明 |
|---|---|---|
| 0 | MOSI | MCU→MT6835 |
| 1 | MISO | MT6835→MCU |
| 2 | SCK | 2.625 MHz（实测半周期 180 ns） |
| 3 | NSS（CSN） | 软件片选 |

两份数据均按此映射解码；解码脚本要求 48 个 SCK、期望发送帧 `A0 03 00 00 00 00`。

## 4. 异常帧细节（转动工况，27 帧）

### 4.1 按原因分布

| `capture_started_with_nss_low; clock_count_not_48; not_expected...; sck_not_idle...` | 1 |

### 4.2 典型异常帧原始数据

```
idx=6163  dur=2760ns  rises=3   falls=4   tx=(空)      rx=(空)
idx=6164  dur=20400ns rises=45  falls=44  tx=00 18 00 00 00  rx=FF FD A9 2A C2
idx=77905 dur=2760ns  rises=3   falls=4   tx=(空)      rx=(空)
idx=77906 dur=20400ns rises=45  falls=44  tx=00 18 00 00 00  rx=FF FD A9 2A C2
idx=84301 ...
```

特征：

- **成对出现**：先是一个 2.76 µs 的"残帧"（仅 3~4 个时钟，tx 为空），紧接着一个
  45 时钟、tx=`00 18 ...` 的错位帧。
- **45 时钟 ≠ 期望 48**：少了 3 个沿。`tx=00 18 00 00 00` 与标准 `A0 03 00 00 00 00`
  相比整体"左移/错位"，正是**时钟边沿在传输中途被吞掉**的表现。
- **idx=0 的 47/46 时钟帧**是采集窗口起点导致的截断（capture_started_with_nss_low），
  不算真实异常；**idx=8812（末帧）是采集结束截断**，同样不算。

## 5. 根因推理链

```
转动 → 功率级带载开关 → di/dt 噪声 → 偶发毛刺到 SCK 线
                                        ↓
                     MCU 的 SPI 采样沿被噪声干扰：
                     某沿被吞（缺时钟）或叠加（多时钟）
                                        ↓
                     边沿错位：后续字节整体左移/右移
                                        ↓
                     MCU 用错位字节重算 CRC → 与传感器 CRC 不一致
                                        ↓
                     固件捕获 crc_error_count++、触发 CRC 故障路径
                                       ↓
         （项目已记录）SPI 外设进入"需 RCC 复位才恢复的坏状态"
                     （spi1_encoder.c 注释：SPE off/on 无法恢复，
                       RCC 复位有效，但只在 PWM OFF 下验证过）
                                        ↓
                     恢复手段在带载下可能无效 → 错误持续累积
```

**三条互为印证的证据：**

1. 逻辑分析仪在引脚上看到：**线上数据全对（CRC=0 错）**；
2. 只有 27 帧时钟异常，且分布与电机噪声一致；
3. 固件侧却稳定捕获 CRC 错（用户观察、`crc_error_count` 增长）——线上对、固件报错，
   中间隔着 MCU SPI 外设这条"最后一程"。

---

## 6. 为什么"静止不错、一转动就错"

| 状态 | 现象 | 机制 |
|---|---|---|
| 静止 | SPI 干净，0 异常帧 | 功率级无电流流动，开关噪声极低 |
| 转动 | 27 帧时钟错位，固件 CRC 错持续 | 带载 di/dt 产生宽带噪声；单帧错位进入外设→坏状态滞留→后续帧即使线上正常也被误判 |

静止与转动的差异**不在传感器、不在 CRC 公式**，而在"线上有无开关噪声"。

---

## 7. 排除的假设

| 假设 | 结论 | 依据 |
|---|---|---|
| 传感器坏了 | 排除 | 线缆上 20 万帧 CRC 全对、报警 0 |
| 接线/虚焊 | 排除 | MISO/SCK 时序干净（160/200 ns 余量） |
| CRC 初值错误（0x00 vs 0xFF） | 排除（对本次现象） | 若初值错，静止时就会全错，与观察不符。**该假设仍未验证，但与本次 CRC 错无关** |
| 编码器上拉缺失 | 非主因 | 线上电平逻辑正确、时序健康 |
| EMI 击穿数据 | **是** | 27 帧时钟错位、成对出现，正是边沿毛刺特征 |

## 8. 修复动作与当前状态（2026-10-22 更新）

> 本版文档更新说明：以下软件修复项在文档初版之后已全部落地，并留有实机记录。
> 软件侧能做的已到位；剩余 CRC 错指向硬件级抗扰，见 8.2。

### 8.1 ✅ 已落地：SPI 提速 + GPIO 速率（软件）

```text
spi1_encoder.h    : SPI_BAUDRATEPRESCALER_16 (10.5 MHz)，SCK 上限 16 MHz 允许
stm32g4xx_hal_msp.c: PA5/PA6/PA7 = GPIO_SPEED_FREQ_VERY_HIGH
```

- 48 SCK 线上时间由 /64 档的 18.286 µs 缩至 4.571 µs，事务受 PWM 开关沿影响的
  窗口缩短约 4 倍。
- 实机记录（`docs/字段/编码器结构体字段说明.md §8.2`）：
  - **零给定中性 PWM 测试通过**：CRC/报警/步长错误均为 0；
  - **enable=1 启动 500 rpm 仍出现 8 次 CRC**（约 0.364 s 内），随后反馈无效停机。
  - 接收 CRC 与离线重算 CRC 的 XOR 依次为 `01 01 01 01 01 03 02 03`——低两位失配特征，
    **不可**据此定位具体单线/单 bit，也不能作为放行坏帧的依据。
- 结论：**提速降低但不消除带载 CRC 错**，与诊断结论（噪声耦合）一致。

### 8.2 ✅ 已落地：SPI 坏帧恢复链重构（软件）

`spi1_encoder.c` 已重构为总线级自持，针对"一帧毛刺 → 外设坏状态滞留"做了四层加固：

| 机制 | 说明 |
|---|---|
| `MT6835_SPI_StopHardware(reset)` | SPE 关、DMA 通道停、清标志与 CNDTR、**RCC 强制+释放复位**清掉移位器/FIFO/错误位；不在中断里等 SysTick |
| 发帧前残留检查 | `TransmitReceiveAsync` 在选片前检查 `BSY/FRLVL/FTLVL/OVR/MODF/FRE`，残留则先 `StopHardware(1)` 再启动 |
| DMA 完成严格判定 | RX TC 后要求 `!BSY && 无 FIFO 残留 && TXE && 两通道 CNDTR==0` 才算完整，否则按错误处理、丢弃整帧 |
| `ResyncIdle` 消除死锁 | 软件空闲时 BSY/CNDTR 残留视为"需要复位"，不再因 BSY 无限拒绝恢复 |

这四项直接对应旧注释里"SPE off/on 无法恢复、需 RCC 复位"的缺陷。

### 8.3 ✅ 已落地：CRC 初值确认（软件/文档）

- `mt6835.h` 注释已从"⚠ 手册未给出初值，按 0x00 假设"改为
  **"经实机验证确认为 0x00（2026-10-22 固化），不可改为 0xFF"**。

### 8.4 ⚠ 剩余：硬件级抗扰（代码无法解决，需板级动作）

逻辑分析仪已证明线上数据正确、时序余量充足，带载下偶发时钟错位是
**功率级开关噪声耦合进 SCK/MISO**。软件提速+恢复只能降低发生率与缩短恢复时间，
**不能消除耦合源**。剩余动作：

- SCK/MISO 串 22 Ω（吸收振铃，靠近 MCU 引脚放）；
- SPI 三线远离功率级与栅极驱动走线；避免与母线/相线并行走线；
- 传感器供电就近加去耦（100 nF + 1 µF），确认无供电跌落引发的 weak_field；
- 缩短逻辑分析仪/示波器探测线（探头本身是天线）；
- 若以上无效且必须根治，评估 MISO/SCK 加 RC 滤波或换更抗扰的编码器接口（如带 CRC+重传的协议层）。

### 8.5 观察手段（已内置，无需改码）

添加 Watch：

| 变量 | 判断 |
|---|---|
| `g_encoder_diagnostics.crc_error_count` | 是否随转动增长 |
| `g_encoder_diagnostics.spi_resync_count / refused_count` | 恢复是否生效/被拒 |
| `g_encoder_diagnostics.busy_trigger_count` | 事务是否超 50 µs |
| `s_encoder.last_crc_match`（最近新增） | 线上对但固件错 → 坐实 MCU 接收侧错位 |

## 9. 遗留未决项

1. ~~CRC 初值假设（0x00 vs 0xFF）~~ → **已确认 0x00**（用户实机验证，2026-10-22 固化）。
2. 带载下 8 次 CRC 的具体耦合路径（哪根线/哪一位）**未定位到 pin 级**——需示波器
   同步抓 SCK/MISO 与 PWM 开关相位来量化；逻辑分析仪（1.65 V 阈值）只能证明电平跳变。
3. 本次分析基于**逻辑电平跳变**，不含模拟振铃/过冲测量；精确量化噪声能量需示波器。
4. 8.4 的硬件抗扰动作尚未验证效果——这是当前唯一有效的剩余方向。
