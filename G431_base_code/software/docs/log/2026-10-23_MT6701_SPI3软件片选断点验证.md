# 2026-10-23 SPI3 软件片选检查

结论：PB6 由软件 GPIO 驱动，通信前拉低，通信结束后拉高，执行顺序正确。

本次先比较板上 Flash 与上次保存的固件，68,008 字节全部一致，
据对应 AXF 定位四个执行点，再用硬件断点读取 GPIO 输入/输出寄存器。
全程 TIM1 MOE=0，电机输出关闭；未修改固件。

## 配置与代码

- PB6 的 MODER[13:12]=01（普通输出），OTYPER[6]=0（推挽）。
- SPI3 CR1.SSM=1（软件 NSS），CR2.SSOE=0、NSSP=0。
- 初始化先写 PB6 高，再配置推挽输出。
- `spi3_encoder.c` 第 60 行拉低 PB6，第 62 行调用阻塞收发，
  第 65 行拉高 PB6；HAL 错误返回同样经过拉高路径。
- 主机测试再次通过，覆盖 HAL 收发期间 CS 为低、结束后 CS 为高，以及超时恢复。

## 板上执行点

| 执行点 | PC | PB6 ODR | PB6 IDR | SPI3 BSY |
| --- | --- | ---: | ---: | ---: |
| 准备调用 GPIO 拉低 | 0x0800A5EA | 1 | 1 | 0 |
| 准备调用 SPI 收发 | 0x0800A640 | 0 | 0 | 0 |
| 收发结束、准备拉高 | 0x0800A686 | 0 | 0 | 0 |
| GPIO 拉高调用返回 | 0x0800A68A | 1 | 1 | 0 |

收发结束点 HAL 返回 HAL_OK（R4=0），TxXferCount=0，RxXferCount=0，
SR=0x00000002（TXE=1、BSY=0）。因此该次 PB6 拉高发生在收发完成之后。

原始日志：`check_cs.log`；解析结果：`cs_check.json`。
操作命令：`check_cs.pyocd`。结束时所有断点已移除，CPU 和周期测试恢复运行，
检查 `cleanup.log`、`after_check.log` 可确认。

## 新观察与范围

被断点延长的该次事务收到 `AD 10 15`：接收 CRC 和固件/电脑独立计算均为
`0x15`，成功产生 1 帧有效数据（角度原码 11076，状态 0）。
随后恢复连续运行，观察到后续约 100 帧仍为 CRC 错误，有效帧总数仍为 1。

硬件断点延长了片选建立时间及帧内停顿，因此该次通过不能代表连续通信已经修复，
也不能仅凭它认定具体是哪一段延时导致失败。它说明值得继续核对实际时序。

本次确认的是 MCU 执行顺序及 PB6 输入寄存器电平。芯片引脚处的模拟电压、
片选脉冲是否有毛刺、CSN 到首个时钟的准确间隔及完整时钟波形，
仍需用示波器或逻辑分析仪验证。
