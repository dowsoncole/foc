## 3. 0x0A 的含义和复位后的根因

### 3.1 旧启动行为

`MainCurrentTest_Service()` 检测 `g_speed_run.enable` 的上升沿。旧版本把输出是否关闭、驱动器状态、ADC 校准、模式、试验占用、编码器换相配置等条件合并检查；任一条件不满足就令 `enable=0`、`fault=10`。

因此 `0x0A` 是十进制 10，即“启动互锁拒绝”。它不是 MT6835 状态寄存器值，不等于高速运行中的编码器故障码。

初始现场证据保存在 [speed_start_0a_board_diagnosis.log](../../control_analysis/results/speed_start_0a_board_diagnosis.log)：当时目标 500 rpm、enable 已被清零、fault=10；模式为电流测试模式、电流 stage 为 dq PI；ADC 校准完成、驱动安全、无运行时故障，但 `calibration_ok=0`。随后使用与板上固件匹配的 Keil 符号复核，内部 `motor_configured=0`、direction=1、pole_pairs=0。

### 3.2 为什么先前能转，重新下载后又不能启动

此前调试过程中，代理通过调试器在 RAM 配置过 `direction=-1`、2 对极和电角零位。`Encoder_ConfigureMotor()` 不只修改公开变量，还配置 encoder 模块内部的方向、极对数、零位和 `motor_configured`，并重建速度历史。

而 `Encoder_Init()` 会清空内部 encoder context。旧代码没有在初始化后再次装入标定参数；`g_speed_test.calibration_ok` 也恢复为 0。机械角度 SPI 采集可以工作，但换相电角度仍未配置。用户只写 enable 时即触发互锁，程序按原设计拒绝转动。

不能只把 `calibration_ok` 的默认值改成 1。那会造成公开状态声称校准完成，但内部换相状态仍未配置。本轮实际调用配置函数，以返回结果决定有效性。

## 4. 板级标定恢复方案

本轮在 `Servo/Inc/speed_commission.h` 建立当前装配专用的标定配置：

```c
#define SPEED_BOARD_ENCODER_DIRECTION (-1)
#define SPEED_BOARD_ENCODER_OFFSET_RAD 5.91902392706f
```

加载函数位于 `Servo/Src/speed_commission.c`：

```c
uint8_t SpeedCommission_LoadBoardCalibration(void) {
    g_speed_test.direction = SPEED_BOARD_ENCODER_DIRECTION;
    g_speed_test.pole_pairs = 2;
    g_speed_test.electrical_offset_rad = SPEED_BOARD_ENCODER_OFFSET_RAD;
    g_speed_test.calibration_ok = Encoder_ConfigureMotor(
        SPEED_BOARD_ENCODER_DIRECTION, 2, SPEED_BOARD_ENCODER_OFFSET_RAD);
    return (uint8_t)g_speed_test.calibration_ok;
}
```

`main.c` 在 `Encoder_Init()` 成功后调用加载函数，再进入主循环。此时输出仍关闭，默认 enable 仍为 0。编码器重新建立速度历史后，启动还要通过新鲜角度/速度/电角度检查。

标定值来自 [此前持续速度调试日志](2026-10-21_持续速度闭环与15A保护调试日志.md) 中的实际 2 A 对齐复核：末段实际 Id 均值约 2.014 A，原始机械角均值约 6.10110461712 rad，采用 direction=-1、2 对极得到 offset 约 5.91902392706 rad。这里只复用已有实测配置，本轮没有再次宣称它是精确到最后小数位的独立计量标定。

该配置通过编译固化，不是运行时新增 Flash 参数存储，也不是每次启动自动对齐。更换电机、改变相线顺序、转动或更换编码器安装位置后必须重新标定，不能继续使用当前 offset。

## 5. 启动诊断位和状态可见性

新增字段 `g_speed_run.start_block_mask` 放在结构体尾部，保留旧前缀字段顺序。读取脚本对应扩展为 60 字节/15 个 32 位字。结构体地址仍须以当前匹配 AXF 解析，不能把地址跨版本硬套。

| 位 | 十六进制掩码 | 名称 | 解释 |
|---|---:|---|---|
| 0 | `0x001` | `SPEED_START_OUTPUT_ACTIVE` | 输出请求、armed、预充电、控制器或 PWM 尚未完全关闭 |
| 1 | `0x002` | `SPEED_START_RUNTIME_FAULT` | runtime 存在锁存故障 |
| 2 | `0x004` | `SPEED_START_CONTROLLER_FAULT` | FOC controller 存在锁存故障 |
| 3 | `0x008` | `SPEED_START_POWER_UNSAFE` | READY/nFAULT 等功率级条件不满足 |
| 4 | `0x010` | `SPEED_START_ADC_NOT_READY` | ADC 电流零偏校准未完成 |
| 5 | `0x020` | `SPEED_START_MODE_INVALID` | requested/active mode 未处于所需电流模式 |
| 6 | `0x040` | `SPEED_START_STAGE_INVALID` | requested/active stage 未处于 dq PI |
| 7 | `0x080` | `SPEED_START_TEST_BUSY` | 电流试验状态不是 IDLE |
| 8 | `0x100` | `SPEED_START_COMMAND_PENDING` | 电流试验、整定或速度试验有未处理命令 |
| 9 | `0x200` | `SPEED_START_CALIBRATION_MISSING` | 编码器换相配置未确认有效 |
| 10 | `0x400` | `SPEED_START_ENCODER_INVALID` | 编码器读取失败，或角度/速度/电角度无效 |

掩码是各条件按位或，可能同时出现多个位。举例 `start_block_mask=0x600` 表示 bit9 和 bit10 同时成立。它和 `fault=0x0A` 是不同变量，不能把 mask 的数值当 fault 编码。

拒绝启动时显式显示 `state=4`、`fault=10`，并保留掩码。成功接受新的启动时，掩码为 0，正常启动经 state1 后进入 state2。程序没有为了让启动通过而自动清除控制器/功率级故障。

此前已修复的 enable 上升沿竞争继续保留：每一轮主循环只采集一次 enable 作为边沿判断的输入，避免调试器恰好在两次读取之间写入 1 时丢失启动请求。当前复位问题的主要原因是校准未恢复，不应再次把全部现象归到已修复的边沿竞争。

## 6. 调试符号误配与初始大量 CRC 错误的证据边界

本轮首先读取了板上 128 KiB Flash，并与已有固件核对。板上内容与旧 `MDK-ARM/servo_v1/servo_v1.axf` 对应映像逐字节匹配；当时的 cbuild AXF 与之有 32 字节差异，涉及 RAM 重定位相关内容。它们不能只因项目名称相同就视为同一份调试符号。

使用不匹配的 cbuild 符号时，曾将 DMA handle 误读为 0。该次关于 DMA handle/寄存器的推断作废，不作为硬件 DMA 未配置或传输失败的证明。之后以正确 Keil 符号复核，见 [encoder_crc_exact_symbols.log](../../control_analysis/results/encoder_crc_exact_symbols.log)。AC6/GDB 的 `pc in CU but not in symtab`、CP1252 编码警告也被保留在日志中；有这些警告不等于全部数值必错，必须按实际地址、类型和匹配映像逐项确认。

初始 `g_speed_run` 前缀和 encoder diagnostics 的地址当时一致，并用正确符号再次复核过，因此初始空闲期间大量 CRC 错误的 episode 本身保留为真实记录，而不是整段删除。原始数据曾显示 CRC 累计数达到百万量级，角度历史长期停留在同一值；这和重新下载本轮固件后初始空闲 CRC=0 的状态不同。

但当时包含调试暂停、外设继续运行、复位及 SPI 状态变化，尚未把这些影响排除，不能据此断言线路损坏或所有 CRC 错误都由高速电机干扰造成。对于新构建版本，重新在输出关闭时解析地址、读取有效反馈和诊断零状态，再开始测试。

## 7. PD2、PA0 的含义及 PD2 抢占问题修正

| 引脚 | 当前软件定义 | 观察范围 |
|---|---|---|
| PD2 | SPI 异步启动前拉高，完整帧解析、CRC/状态检查、有效/无效反馈发布完成后拉低 | 整个 encoder 事务的软件包络，包括等待 DMA 完成的时间 |
| PA0 | 注册的 FOC conversion callback 调用前拉高、返回后拉低 | FOC callback 执行时间，不是整个 ADC IRQ 的全部前后开销 |

两个引脚由 `Core/Src/gpio.c` 配置为推挽输出、空闲低电平，事件中使用 GPIO BSRR 直接置位/复位。PA0 代码在 `Modules/Current_Sampling/Src/current_sampling.c`，PD2 代码在 `Modules/Encoder/Src/encoder.c`。ADC 完整 IRQ 的 DWT 统计仍保留，它与 PA0 脉宽定义不同。

旧的 encoder 完成路径可能先清 `transfer_busy`，再拉低 PD2。若 TIM1 在两次写之间抢占，下一次事务会拉高 PD2，然后旧回调返回再将其拉低，造成正在传输时 PD2 意外为低。它会破坏示波器测量标记，不能直接用此异常波形推断实际 SPI 已经结束。

本轮采用以下顺序，并用短临界区保证两个状态发布的一致性：

```c
uint32_t mask = Encoder_IrqSave();
GPIOD->BSRR = ((uint32_t)GPIO_PIN_2 << 16U);
s_encoder.transfer_busy = 0U;
Encoder_IrqRestore(mask);
```

也就是先公布 PD2 已空闲，再允许下一事务启动。SPI 启动失败路径及时将 PD2 拉低。超时/传输异常最终也要通过完成/错误处理释放该包络。此修复针对 GPIO 时序标记竞争，不等于已经修复所有 CRC 或高速报警。

SPI MSP 初始化还显式执行 SPI1 外设复位，再写入 HAL 初始化配置，以避免调试器复位留下旧 SPE/波特率状态影响新的首帧。这个措施处理复位一致性，不以它解释所有运行中错误。

本轮未保存独立示波器截图来对上述脉宽作最终计量验收；现有依据为源代码、构建及运行诊断。

## 8. 错误原始帧与报警语义

新增 `g_encoder_fault_capture` 保存第一条错误、最后一条错误、8 条环形错误和最后一条传感器报警。每条记录包含 DWT cycle、原因、上一有效角度、上一有效帧时间、SPI SR、6 字节 RX、软件计算 CRC、状态低3位。

CRC 错误和状态报警分开处理：先验证 CRC；只有 CRC 正确，才把低3位解释为有效的传感器报警。坏帧里出现低3位 `7` 并不能证明三个实际报警同时出现。

实际处理保存在 `Encoder_TransferComplete()`：CRC不匹配时记录错误，但不发布坏角度；只有上一有效角度仍在原有150μs年龄预算内，才可继续使用其原始时间戳和序号。CRC通过后再检查传感器报警；通过全部检查才发布新快照。没有延长旧数据的时间戳来掩盖连续丢帧。

厂商手册和本工程定义将状态 bit0 命名为 overspeed warning、bit1 弱磁场、bit2 欠压。原始手册可查 [MT6835 Rev.1.3](https://www.magntek.com.cn/upload/pdf/202407/MT6835_Rev.1.3.pdf)。本轮电机编码器速度读数只有约 2407 rpm，因此读到 bit0=1 时，只能确认“接收到了 CRC 正确、bit0 置位的报警帧”，不能进一步宣布转子真实机械速度已超过器件最高速度，也不能擅自屏蔽该位继续运行。

官方英文手册§7.6.2给出的SPI约束为：CS下降至第一个SCK下降至少100ns，时钟周期至少60ns，高/低电平各至少30ns，最后SCK上升至CS上升至少半个时钟周期；§7.6.8及寄存器页说明CRC覆盖ANGLE21位和STATUS3位，多项式为0x07。以上是器件规格核对，不是本轮已用示波器证明每一项边沿时序合格；仅改变分频不能替代CS保持时间或信号完整性的实测。

捕获使用 32 位 DWT 计数器，在 168 MHz 下约 25.6 秒回绕。跨很长时间比较两次错误必须考虑回绕；环形记录会覆盖；过流结构本轮没有同步 DWT 时间戳。后续即使看到一条 CRC 错误与一条过流记录，也不能仅比较累计次数就确定先后因果。

## 12. 为什么这次 fault11 可以确认直接停机路径

`main.c` 的ADC回调先读取/换算电流，再执行相电流保护，然后才进入正式FOC。软件逻辑顺序为：

1. 输出armed时，检查 U/V/W 是否有限及是否超过本次阈值。
2. 若超过15 A，记录 `g_current_trip` 的序号、电流、原始ADC。
3. 清 output_request/armed，设置 controller/runtime 的 CURRENT_INVALID(bit0)，调用Stop并立即返回。
4. 后台看到控制器故障，将连续速度模式状态设为4；若此前没有速度专用故障，则填通用11。

所以本次 `current_trip.count=1`、runtime/controller flags=1、phase_peak=17.338 A 和fault11是相互一致的。这个ADC周期在保护后直接返回，未继续运行速度反馈读取及电流控制器。

这只确认本次停止的直接软件原因。它不能反推第一个物理异常是什么。10.5 MHz那轮则是current_trip=0、runtime flags=6、CRC正确的status1帧，属于不同证据链，不能混写成同一种过流故障。
