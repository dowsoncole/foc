## 新发现

### [P2] 电压斜坡在输出未授权时仍推进，再次启动可能直接施加目标电压

位置：Core/Src/main.c:423–441、749–755、799–802；FOC/Src/foc_algorithm.c:130–158。
电压开环每次 ADC 回调先调用 FOC_AlgorithmVoltageStep，之后才检查 output_armed/precharge_in_progress。算法会更新 applied_d/q_voltage_v，因而输出关闭期间也会推进电压斜坡。
停止分支只在 armed 或 MOE 非零时将 applied 电压清零一次。之后 ISR 又开始累加；再次启动的电压分支只设置 output_armed，没有重新初始化斜坡。
触发示例：设置非零目标电压和 0.5 V/s 斜坡，保持输出 OFF 足够久，再置 output_request。预充结束后的首个实际输出可以已经达到目标值，而不是从零开始缓升。初次启动前等待也有同类问题。
建议：区分用于纯算法观察的模拟状态和用于实际输出的斜坡状态；实际输出斜坡应在明确的启用边界重置并仅随有效输出周期推进。
验证：OFF 等待超过目标电压/斜坡速率，再 ON，记录首个应用电压和后续每周期增量；无需带载即可先做端口 mock 验证。

### [P2] 电压开环停止顺序允许中断在关断后重新置 MOE

位置：Core/Src/main.c:749–756；同文件 437–440、460–464。
主循环先 EmergencyStop，再清 applied 电压，最后才清 output_armed。在 EmergencyStop 和清 armed 之间，ADC ISR 仍看到 armed=1；ISR 不检查 output_request，且在 safe、fault_flags=NONE、MOE=0 时重新调用 EnableOutputs。
因此 OFF 操作期间可能发生“主循环关断 → ISR 重新开启 → 主循环撤销 armed”的交错。下一轮主循环通常能再次关断，但两次之间存在非预期输出窗口，不能宣称 OFF 已连续保持关断。
建议：在保留原中断屏蔽状态的短临界区中先撤销授权再关断，并统一输出状态发布；不要把延时或计算放入临界区。
验证：在关断调用返回后、armed 清零前注入一次模拟 ADC 回调，断言 MOE 在 OFF 后不可再次置位。

### [P2，接口潜在风险] ISR 故障邮箱的读后清零会丢失新事件

位置：Servo/Src/servo_manager.c:122–127、153–154。
Service 分两条语句读取 pending_faults 再写 NONE；若 RaiseFaultFromIsr 在两者之间置位，新故障会被后续清零覆盖，且不在本次 detected_faults 内。volatile 不能使读并清零成为原子操作。
本次没有在实际主流程发现该 ISR 上报接口的调用，因此此项属于接口接入前需解决的潜在缺陷，不宣称当前板上已经丢失事件。FOC 自身 fault_flags 的另一路映射也不能替代所有仅通过邮箱上报的事件。
建议：提供平台临界区或原子交换端口，将故障取出与清空合为一次受保护操作；用确定性的交错测试覆盖该窗口。

## 结构优化建议

1. 将正常模式与开环模式共享的授权、预充、停止、故障锁存提取为统一输出生命周期，避免 main 与 ServoManager 各自维护不同保护规则。
2. 对主循环/ISR 共享状态明确唯一写入者及发布边界；多字段命令用快照或双缓冲，故障邮箱用原子交换。
3. 将开环算法计算与实际输出斜坡状态分离，保留关闭输出时观察数学波形的能力，同时保证真实启动具有独立且可测试的缓升过程。
4. 为现有主机测试增加启停交错与故障邮箱测试；在 CI 固定可用 C 编译器，避免测试只能依赖开发机环境。
5. 后续独立清理已跟踪的构建产物，降低提交噪声。本次不修改忽略规则或工程配置。
